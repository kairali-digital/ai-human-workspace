# Kairali Rahul Sales System

Use Rahul Jain's principles indirectly to make Kairali sales observable, teachable and improvable. Do not reproduce or present his programme as Kairali-owned theory.

For Kairali work, invoke this exact governed skill name. Do not substitute another generic sales framework or auto-select this skill for unrelated sales-adjacent work.

## Read first

Read:

- `references/sales-system-workflow.md` for the adapted operating model and output contract.
- `references/kairali-boundaries.md` for safe scope, ethical adaptation and Gate 0.
- `references/source-index.md` when provenance, missing weeks, or source limitations matter.

## Route the request

Choose one primary mode:

1. **MAP** — describe the current lead-to-repeat process, owners, handoffs and evidence.
2. **DIAGNOSE** — find leakage, overload, unclear roles, missing data or coaching gaps.
3. **DESIGN** — propose a bounded pilot process, checklist, review or practice loop.
4. **REVIEW** — challenge a supplied sales system, CRM flow, MIS or operating proposal.

Do not implement organisation, staffing, CRM, access, pay, target or policy changes unless separately authorised.

## Observe before prescribing

Gather the minimum material facts:

- role/business lane and buyer type;
- current process and actual handoffs;
- NBD versus CRR work;
- current authorised systems and fields;
- available stage evidence and dated results;
- approved targets, prices, claims and offers;
- specific failure or decision to improve.

If data is absent, propose what to observe. Never invent a target, ratio, baseline, capacity, conversion rate, staffing number or expected uplift.

## Apply the sales-system spine

- Separate pure selling from repeatable coordination and sales operations.
- Map NBD and CRR; distinguish lead, before-order, order, post-order/service and repeat stages.
- Use SPIN as Kairali's live discovery-questioning spine.
- Translate features into customer-relevant benefits, then support with approved proof.
- Make each stage's owner, input, action, handoff, evidence and exception visible.
- Review actions and stage movement, not only end targets.
- Build practice: call observation, roleplay, feedback, retraining and manager sign-off.

Treat deep division of labour as a diagnostic principle, not an automatic reorganisation. Preserve human judgment and test one bounded pilot before scale.

## Analyse the numbers without inventing them

When inputs exist, show the formula and source for each number. Useful relationships include:

- stage conversion = stage exits / stage entries;
- sales capacity = available selling time / observed time per selling activity;
- expected output = opportunities × observed conversion × approved average value;
- repeat health = eligible customers contacted, reordered, retained, or escalated.

If the data does not support a calculation, mark it `UNKNOWN` and define the observation needed.

## Required output

Return:

1. **System verdict** — `READY TO PILOT`, `REVISE`, or `BLOCKED`.
2. **Current-state evidence** — confirmed facts, unknowns and sources.
3. **Flow** — stages, roles, handoffs and proof.
4. **Leakage/risks** — process, customer, data, ethics and workload.
5. **Bounded pilot** — one lane, owner, duration decided by the owner, checks and rollback.
6. **Review loop** — what a manager observes and how learning is recorded.
7. **Next single action** — one bounded step.

Read the active local gate IDs from the worker's `GATES.md`. If one is crossed, name
it and stop at its approval path. For health/treatment, certification, regulated
wording, staffing policy, price/discount, access, customer-data permissions or other
uncertain consequential content not yet covered by a confirmed profile, route a
reviewable proposal to the named compliance owner. These public risk examples do not
create one Kairali-wide Gate 0.
